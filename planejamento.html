Monitor de Presenças

App web mobile-first (PWA) para estudantes registrarem faltas em segundos, verem a margem de segurança de cada matéria em tempo real, receberem alertas antes de reprovar e compartilharem a grade com colegas. Tudo passa por um backend próprio; o navegador nunca toca no banco.

O que mudou da v1 para a v2
  • Supabase removido por completo (Auth, RLS por auth.uid(), pg_cron).
  • Backend dedicado (API + worker) entre o front e o banco. O front não tem credencial de banco e não importa nenhum código de acesso a dados.

  • PostgreSQL próprio em rede privada, com papéis separados, RLS forçado como segunda camada e backups com teste de restauração.
  • Quatro tabelas novas de acesso e confiabilidade: auth_accounts, sessions, auth_tokens, idempotency_keys.

Princípios e stack

Regras que não se negociam

Estas cinco regras guiam todas as escolhas abaixo. Qualquer atalho que quebre uma delas fica de fora.

1
O navegador nunca fala com o banco.Só a API e o worker têm credenciais. O Postgres fica em rede privada, sem porta pública. Uma regra de lint impede o app web de importar o pacote de banco.
2
Toda regra de negócio roda na API.O front exibe e pede. Cálculo de limites, alertas, permissões e validação final acontecem no servidor; o front só repete a validação para dar resposta rápida ao usuário.
3
Toda escrita é transacional e a contagem é derivada.Não existe contador de faltas salvo. O total sai sempre dos registros, dentro da mesma transação que grava a falta e enfileira o alerta.
4
Isolamento em duas camadas.A API filtra tudo por usuário e o Postgres aplica Row-Level Security forçado. Um bug numa camada não expõe dados de outra pessoa.
5
O banco só muda por migration.Migrations SQL versionadas, revisadas no PR, testadas no CI contra um Postgres real e aplicadas por um passo próprio do deploy. Ninguém altera o banco à mão.

Arquitetura do backend

Três serviços, um banco protegido

O web serve a interface. A API concentra regras, autenticação e acesso a dados. O worker envia alertas e roda tarefas agendadas. Só os dois últimos enxergam o banco.

Caminho de uma requisição

Navegador / PWAapps/web

Formulários com validação Zod para resposta rápida. Cliente HTTP gerado do OpenAPI. Nenhum segredo, nenhuma credencial de banco.

fronteira de confiança · nada abaixo daqui confia no cliente
Borda HTTPFastify + plugins

Cabeçalhos de segurança (helmet), checagem de Origin em escritas, rate limit no Redis, limite de tamanho do corpo, request_id.

Controllersapps/api/src/*/controller

Validam corpo, query e parâmetros com os schemas de packages/contracts. Erros saem no formato padrão application/problem+json (RFC 9457) com código estável, ex.: ATTENDANCE_CONFLICT.

GuardsSessionGuard · VerifiedGuard

Resolvem a sessão pelo cookie, carregam o usuário, exigem e-mail verificado onde necessário.

Casos de usoservices

Abrem a transação, definem app.user_id, chamam repositórios e o motor, gravam outbox e auditoria. Um caso de uso por ação (RecordAttendance, ImportTemplate…).

Domíniopackages/engine

Motor de cálculo puro, sem I/O, 100% testado. A API é a autoridade; o front usa o mesmo pacote só para a prévia enquanto o aluno digita.

Repositóriospackages/db

Drizzle. Toda consulta recebe userId explicitamente. Nenhum SQL montado por concatenação.

PostgreSQLrede privada · TLS

Restrições de integridade, RLS forçado, view de totais, triggers de auditoria. Último guardião: recusa dado inválido mesmo que o código erre.

Barreira no build: uma regra do dependency-cruiser no CI falha se apps/web importar packages/db ou qualquer driver de Postgres. A separação entre front e banco não depende só de disciplina.

Concorrência e idempotência

  • Registrar presença exige o cabeçalho Idempotency-Key. A primeira resposta fica salva em idempotency_keys por 24 h; repetir a chamada devolve a mesma resposta sem gravar de novo.
  • Editar exige If-Match com a versão do registro. Se outro dispositivo editou antes, a API responde 412 e o app mostra o valor atual.
  • SELECT … FOR UPDATE na matéria serializa registros simultâneos.

Erros e respostas

  • 422 para validação, com o campo e a mensagem em português.
  • 401 sem sessão, 403 sem permissão, 404 também para recurso de outro usuário (não revela que existe).
  • 409 para conflito de ocorrência, 412 para versão desatualizada, 429 com Retry-After.
  • 500 nunca expõe stack trace; mostra só o request_id para suporte.
Autenticação

Autenticação própria dentro da API

Nada de serviço externo de identidade. Usamos primitivas consagradas (Argon2id, tokens aleatórios de 256 bits, OAuth 2.0 com PKCE) e guardamos só hashes no banco.

Senhas

  • Hash Argon2id com os parâmetros da OWASP (19 MiB, 2 iterações, paralelismo 1).
  • Mínimo de 10 caracteres, checagem contra senhas vazadas (Have I Been Pwned por k-anonimato, sem enviar a senha).
  • Login com o mesmo tempo de resposta exista ou não a conta.

Sessões

  • Token opaco de 32 bytes no cookie __Host-sid (HttpOnly, Secure, SameSite=Lax). No banco fica só o SHA-256 dele.
  • Validade de 30 dias, renovada com o uso; expira após 14 dias parado.
  • Trocar a senha encerra todas as sessões. O aluno vê e encerra sessões de outros dispositivos.

Google

  • OAuth 2.0 Authorization Code com PKCE e state, feito pela API (biblioteca Arctic).
  • Só aceita e-mail que o Google marca como verificado.
  • Vincula à conta existente com o mesmo e-mail apenas se essa conta já tiver o e-mail verificado.

Magic link, verificação e recuperação

  • Todos usam auth_tokens: token aleatório, só o hash no banco, uso único, validade de 15 min (magic link e senha) ou 24 h (verificação).
  • "Esqueci a senha" responde igual exista ou não a conta.
  • Rate limit por IP e por e-mail em todas essas rotas.
Proteção contra CSRF: como o front chama a API pelo mesmo domínio, o cookie é SameSite=Lax e toda escrita exige cabeçalho Origin igual ao domínio do app. Requisições de outros sites são recusadas antes de chegar ao controller.

Papéis do banco e RLS sem Supabase

A API não se conecta como dona das tabelas. Cada transação começa dizendo quem é o usuário; as políticas de RLS leem esse valor. Se a API esquecer de defini-lo, a consulta não retorna nada: a falha é fechada.

-- quem é dono das tabelas não é quem a aplicação usa
create role app_owner  nologin;   -- dono do schema; só o passo de migration assume este papel
create role app_api    login;     -- só SELECT/INSERT/UPDATE/DELETE; sem BYPASSRLS, sem DDL
create role app_worker login;     -- só as tabelas de notificação e leitura do necessário

-- a API abre cada transação assim (true = vale só dentro desta transação)
begin;
select set_config('app.user_id', $1, true);
-- … consultas do caso de uso …
commit;

alter table attendance_logs enable row level security;
alter table attendance_logs force row level security;   -- vale até para o dono
create policy owner_all on attendance_logs to app_api
  using      (user_id = nullif(current_setting('app.user_id', true), '')::uuid)
  with check (user_id = nullif(current_setting('app.user_id', true), '')::uuid);
-- o nullif evita erro de conversão quando a variável ficou vazia após outra transação
Integridade entre donos: as FKs filhas são compostas, por exemplo (semester_id, user_id) → semesters(id, user_id). O banco recusa ligar uma matéria ao semestre de outra pessoa, mesmo que um bug no código tente.

View de totais: a fonte única da verdade

Não existe contador de faltas armazenado. Os totais são sempre derivados de attendance_logs por uma view com security_invoker (respeita o RLS de quem consulta). Clique duplo, queda de conexão ou edição não fazem o número divergir, porque não há número separado para divergir. Com algumas centenas de registros por aluno, a soma leva poucos milissegundos com o índice (subject_id, class_date).

create view subject_totals with (security_invoker = true) as
select s.id as subject_id,
  coalesce(sum(l.units_missed) filter (where l.status in ('absent','partial')
           and (not l.is_excused or s.excused_policy = 'track_only')), 0) as units_counted,
  coalesce(sum(l.units_missed) filter (where l.is_excused), 0)          as units_excused,
  coalesce(sum(l.units_scheduled) filter (where l.status <> 'cancelled'), 0) as units_held,
  count(l.id)                                                           as logs_count
from subjects s
left join attendance_logs l on l.subject_id = s.id
group by s.id;

Restrições que protegem os dados

-- o status e a quantidade perdida precisam concordar
alter table attendance_logs add constraint logs_status_units_chk check (
  (status = 'present'   and units_missed = 0) or
  (status = 'absent'    and units_missed = units_scheduled) or
  (status = 'partial'   and units_missed between 1 and units_scheduled - 1) or
  (status = 'cancelled' and units_missed = 0 and not is_excused)
);

-- uma ocorrência de aula = um registro
alter table attendance_logs add constraint logs_one_per_occurrence
  unique nulls not distinct (subject_id, class_date, schedule_id);

-- tokens e sessões: só o hash, com validade obrigatória
alter table auth_tokens add constraint tokens_expiry_chk check (expires_at > created_at);

Migrations sem tirar o app do ar

  • O Drizzle gera o SQL; o arquivo entra no PR e é revisado como código.
  • O CI aplica todas as migrations do zero num Postgres em container e roda os testes de integração em cima.
  • No deploy, um job separado aplica as migrations com o papel app_owner antes de subir a nova versão da API.
  • Mudanças destrutivas seguem expandir e contrair: cria a coluna nova, migra os dados, troca o código, remove a antiga numa versão seguinte.

Como funciona o compartilhamento

Gerar

  1. O aluno escolhe um semestre ou uma matéria e toca em "Compartilhar".
  2. A API monta um snapshot em payload: nomes, regras de contagem, horários, sala e professor. Faltas nunca entram.
  3. Gera um código de 8 caracteres (ex.: K7QM-4XPT) e um link /importar/K7QM4XPT com QR code.

Importar

  1. O colega abre o link; GET /v1/templates/:code devolve só a prévia (título, curso, matérias), com rate limit por IP.
  2. Ao confirmar, um caso de uso valida o payload com Zod e cria semestre, matérias e horários numa transação só.
  3. A matéria guarda source_template_id só como referência; editar o modelo depois não altera a cópia de ninguém.
Etapa 2 · Motor de cálculo acadêmico

De carga horária a saldo de faltas

Um pacote TypeScript puro (packages/engine), sem dependências e sem acesso a banco. A API usa para responder, gerar alertas e exportar; é a fonte oficial dos números. Tudo é convertido para tempos de chamada, a menor unidade em que a faculdade conta presença.

Vocabulário

  • Encontro: uma aula no calendário (ex.: terça 19h–20h40).
  • Tempo: unidade de chamada. Um encontro geminado pode valer 2, 3 ou 4 tempos.
  • T: total de tempos no semestre. F: máximo de tempos que podem ser perdidos.
  • A: tempos perdidos que contam. R = F − A: saldo.
  • p: presença mínima em centésimos de ponto percentual (75% → 7500).

Três modos

  • Por aulas: T = aulas × tempos_por_aula; F = ⌊T × (10000 − p) / 10000⌋
  • Por carga horária: min = horas × minutos_da_hora (60 para hora-relógio, 50 ou 45 para hora-aula); T = ⌊min / min_por_tempo⌋; F = ⌊min × (10000 − p) / (10000 × min_por_tempo)⌋
  • Limite manual: F informado pelo aluno; T vem das aulas, se informado.
Arredondamento sempre a favor do aluno. O limite usa piso (⌊ ⌋) e a conta é feita só com inteiros. Em ponto flutuante, 40 × (1 − 0,8) dá 7,999999999999998, e o piso viraria 7 em vez de 8: o aluno perderia uma falta legítima. Com inteiros, 40 × 2000 / 10000 = 8, exato. A porcentagem exibida também é truncada (74,96% aparece como 74,9%, nunca 75,0%).
export function maxAbsenceUnits(r: SubjectRules): number {
  const allowedBp = 10_000 - r.minAttendanceBp;           // 7500 → 2500
  switch (r.mode) {
    case 'class_count':
      return Math.floor((r.totalClasses * r.unitsPerClass * allowedBp) / 10_000);
    case 'workload': {
      const minutes = Math.floor(r.workloadHours * r.workloadHourMinutes);
      return Math.floor((minutes * allowedBp) / (10_000 * r.unitMinutes));
    }
    case 'manual':
      return r.manualMaxUnits;
  }
}

export function riskLevel(A: number, F: number, unitsPerClass: number): Risk {
  if (A > F)  return 'failed';                               // reprovado por falta
  if (A === F) return 'limit';                               // no limite, ainda aprovado
  const classesLeft = Math.floor((F - A) / unitsPerClass);
  if (A * 100 >= F * 75 || (A > 0 && classesLeft <= 2)) return 'critical';
  if (A * 100 >= F * 50) return 'warning';
  return 'safe';
}

// presença projetada se o aluno for a todas as aulas restantes, truncada em 1 casa
export const projectedPresence = (T: number, A: number) =>
  T === 0 ? 0 : Math.floor(((T - A) * 1000) / T) / 10;

A regra de "restam 1 a 2 faltas" só vale depois da primeira falta, para que uma matéria com margem curta não comece laranja com zero faltas. A unidade (encontros ou tempos) está nas decisões em aberto.

Casos de borda tratados

  • F = 0 (presença de 100% exigida): qualquer falta já é reprovação; o card mostra "sem margem".
  • Saldo negativo aparece como "excedeu em N tempos", nunca como número negativo solto.
  • Falta parcial (chegou atrasado e perdeu o 1º tempo) soma só os tempos perdidos.
  • Aula cancelada ou feriado não conta falta nem presença.
  • Atestado: com deduct sai da conta; com track_only conta, mas fica marcado para controle pessoal.
  • Mudança de presença mínima ou carga no meio do semestre recalcula tudo na hora, porque nada é armazenado.
Etapa 3a · Arquitetura de alertas

Alertas confiáveis com outbox transacional

O alerta nasce na mesma transação que grava a falta. Se a transação falhar, não existe alerta; se der certo, o alerta está garantido na fila, mesmo que o envio de e-mail caia. Quem envia é o worker, um processo separado da API.

flowchart TD
  A["Toque em Faltei"] --> B["POST /v1/attendance com Idempotency-Key"]
  B --> C["Guard de sessão + validação Zod"]
  C --> D["BEGIN, define app.user_id, trava a matéria"]
  D --> E["Upsert do registro"]
  E --> F["Totais pela view subject_totals"]
  F --> G["Motor avalia marcos 50/75/90/100"]
  G --> H["Insere notification_logs pendentes"]
  H --> I["COMMIT e resposta 201"]
  I -.-> J["NOTIFY outbox"]
  J --> K["Worker"]
  L["Varredura a cada 30 s"] --> K
  K --> M["E-mail via Resend"]
  K --> N["Web Push VAPID"]

Na API (dentro da transação)

  1. SELECT … FOR UPDATE na matéria serializa registros simultâneos (dois celulares, clique duplo).
  2. Upsert protegido por Idempotency-Key e pela unicidade da ocorrência.
  3. O motor calcula o consumo e compara com subject_threshold_state.
  4. Para cada marco recém-cruzado, insere linhas em notification_logs com dedupe_key única. O aviso in-app já entra como sent.
  5. Um trigger faz pg_notify('outbox') para acordar o worker na hora.

No worker (fora da transação)

  1. Acorda pelo LISTEN outbox e também varre a fila a cada 30 s, caso alguma notificação se perca.
  2. Pega lotes com FOR UPDATE SKIP LOCKED: duas instâncias nunca pegam a mesma linha.
  3. Resend recebe Idempotency-Key = notification.id; retentativa com backoff exponencial, até 5 vezes, depois failed com alerta no Sentry.
  4. Push com resposta 404/410 apaga a inscrição morta.
  5. pg-boss agenda lembretes de check-in, limpeza de sessões expiradas e de chaves de idempotência antigas.

Idempotência e rearme dos marcos

Cada matéria tem um estado por marco: armed e cycle. A chave de deduplicação é threshold:{subject_id}:{pct}:{cycle}, única por canal no banco. Um e-mail repetido sobre o mesmo marco é impossível, a menos que o aluno desça abaixo dele e cruze de novo.

Canais

  • E-mail (React Email): matéria, faltas registradas, limite, saldo em tempos e encontros, botão para abrir o app.
  • Web Push: título curto ("Cálculo II: restam 2 aulas"). No iPhone exige o app instalado na tela inicial (iOS 16.4+); o onboarding explica isso.
  • Central in-app: sino com contador, lido/não lido via read_at.

Lembrete de check-in

  • Diário (horário escolhido) ou semanal (dia escolhido), no fuso do aluno.
  • O worker calcula a hora local de cada usuário e usa a chave checkin:{user}:{data_local}.
  • Com A13, só dispara se houver aulas da grade sem registro, e respeita o horário silencioso.

  • Cabeçalho institucional mesclado, fundo azul-tinta e texto branco em negrito.

  • Impressão em paisagem, ajustada à largura de uma página.

Segurança e operação

Defesa em camadas e banco que não se perde

Segurança

  • Banco sem porta pública; só API e worker, pela rede privada, com TLS.
  • Papéis separados: app_api e app_worker não criam nem alteram tabelas e não ignoram RLS.
  • RLS forçado e FKs compostas com user_id como segunda camada de isolamento.
  • Testes de isolamento no CI: o usuário B tenta ler, editar e apagar dados do A em cada rota; todos precisam falhar com 404.
  • Segredos só em variáveis de ambiente do servidor, validadas com Zod na inicialização. A API não sobe se faltar algum.
  • Rate limit: login 5/min por IP e e-mail, magic link 3 a cada 15 min, prévia de código 20/min por IP, exportação 10/h por usuário.
  • Revisão final contra o checklist OWASP ASVS nível 2 antes do lançamento.

Operação

  • Postgres gerenciado com PITR: dá para voltar o banco a qualquer minuto dos últimos 7 dias.
  • Dump lógico diário criptografado num armazenamento separado do provedor do banco.
  • Teste de restauração mensal automatizado: restaura o dump num banco novo e roda verificações.
  • Pool de conexões na API com limite e timeout de consulta (statement_timeout de 5 s).
  • Rotas /healthz e /readyz; o deploy só troca de versão quando a nova responde pronta.
  • Sentry e alertas para erro 5xx, fila do outbox parada e envios falhos.
  • Teste de carga com k6 antes do lançamento (meta: p95 abaixo de 200 ms em POST /v1/attendance).
